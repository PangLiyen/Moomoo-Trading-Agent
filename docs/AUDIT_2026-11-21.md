# Self-commissioned audit — 2026-11-21

An agent with no stake in the result was asked to read every claim in
`docs/STRATEGY.md` and `docs/PRE_REGISTRATION.md` against `engine/`,
`config/risk_limits.yaml` and the broker record, and to list every divergence
however small. It was told explicitly to find what the author had missed.

It returned 26 findings. All are recorded here, including the three that say
documents in this repository currently make false claims.

This document exists because the alternative was to fix the findings quietly
and present a clean repository. A clean repository proves nothing about the
process that produced it. A list of 26 defects found by looking, with dates
and dispositions, is the actual evidence.

---

## 1. Provenance — three claims that did not hold

### P-a — the ledger's genesis record pins the wrong commit

`logs/decisions.jsonl` seq 1 records `code_commit: "5748462"`. At that commit
`run_cycle.py`, `engine/signal.py`, `engine/risk_gate.py`, `engine/sizing.py`
and `engine/account.py` **do not exist** — they were added in `0a91ffc`.

`ledger.py`'s own docstring claims the genesis record "pins the rules **and the
code** to the chain's root." For that ledger file, it pinned the rules and a
commit that contained no code. The value is operator-supplied through
`--code-commit`, and the operator passed `git rev-parse HEAD` at a moment when
the engine was still uncommitted.

**Severity: high.** Not a mechanism failure — the mechanism recorded faithfully
what it was given. A pinning error, which is worse in one respect: the record
looks correct.

**Disposition.** The existing genesis record stands; it is in a hash chain and
rewriting it would be the exact act the chain exists to detect. The live run
starts a new ledger whose genesis pins the commit that contains the engine, and
`run_cycle.py` will verify that `engine/` actually exists at the commit it is
handed rather than accepting any string.

### P-b — the rules hash in STRATEGY.md's header is not the config in force

Header: `c0ca0cf8…`, the config at `5748462`. In force: `f03bc61c…`, committed
at `0a91ffc`.

Scoped precisely, because the broad version of this finding would be worse than
the true one. Exactly two enforced values differ:

| value | at 5748462 | in force | direction |
|---|---|---|---|
| `fees.commission_per_filled_order_usd` | 0.99 | **1.00** | more conservative |
| `fees.round_trip_cost_usd` | 1.98 | **1.99** | more conservative |

Every sizing and risk parameter is byte-identical: `risk_per_trade_pct` 0.35,
`sizing_risk_distance_atr_mult` 1.5, `max_position_notional_pct` 15.0,
`min_position_notional_usd` 3000, and the five `min_atr20_usd` gates.

The commission figure is read by `size_position`'s cost gate, so this *is* a
behavioural change, not only a recorded fact. It was made because a completed
sell settled at exactly $1.0000 — `balance 99285.340 → 99990.765` on a fill of
706.425 — against a $0.99 reservation. The higher figure makes the gate
stricter, so the change can only refuse trades the old value would have
allowed.

**Addendum 1 overstated this** when it said `config/risk_limits.yaml` is
"unchanged except for recording measured facts." A number the cost gate reads
did move. Corrected here.

**Disposition.** The header keeps the `5748462` hashes, because that is what was
committed before trading and the point of a hash is that it does not follow the
file. This note is the bridge. The live ledger's genesis will pin `f03bc61c`.

### P-c — documents claiming to be committed were not committed

`docs/PRE_REGISTRATION.md` states it was "committed before the agent was
deployed." `git status` showed it untracked. The same was true of
`docs/HYPOTHESIS_TESTS.md`, both addenda to `docs/STRATEGY.md`,
`tests/test_outlier_filter_is_causal.py`, `analysis/verify_implementations.py`,
and the `engine/signal.py` that was actually running.

**Severity: high, and the most embarrassing finding in this list.** A
pre-registration that is not committed is not a pre-registration. It is a file
its author could edit on Tuesday. Every claim resting on "this existed before
the outcome" was unsupported for as long as the file sat untracked.

**Disposition.** Committed and pushed before the first strategy trade. The
timestamp is what it is — 2026-11-21, not earlier — and no claim is made that
it predates the measurements it discusses.

## 2. Controls that are specified, tested, and not wired

The pattern the audit kept finding is the same one that produced the account
guard tautology earlier: **logic that is correct and tested, reached by a
caller that does not supply its inputs.** Gate-level tests pass fixtures
directly, so they cannot catch a driver that passes zeros.

| # | Control | Status | Why it cannot fire |
|---|---|---|---|
| N3 | Daily loss halt, drawdown flatten, consecutive-loss stop, cycle-gap flatten, entry spacing | **inert** | `run_cycle.py` hardcodes `session_pnl_pct=0.0`, `peak_drawdown_pct=0.0`, `consecutive_losses=0`, `seconds_since_last_entry=None`, `seconds_since_last_completed_cycle=0.0`. `AGENT_MODE` is never read |
| N6 | All five exits | **not implemented** | `evaluate_exit` has zero callers and zero tests. No exit path, no flatten scheduler, no exit ledger record |
| N7 | Holiday stop, 27 Nov 12:45 ET | **not implemented** | `holiday_flat_by` is a parameter nobody passes; `calendar_overrides` is never read |
| N8 | Session stop 15:50, time stop 60 min | **function defaults** | `flatten_all_by_et` and `execution.max_holding_minutes` are unread |
| N12 | RTH-only, 5-minute bars | **not enforced** | `ET_SESSION_OPEN`/`ET_SESSION_CLOSE` are defined and never used; `load_bars` accepts any bars at any interval |
| N4 | 10:00 entry floor | hard-coded | `session.earliest_entry_et` is dead config |
| N19 | "Risk auditor may tighten at runtime" | declarative | `RiskConfig` has no setters; tightening needs a YAML edit and a restart |
| N23 | Order attribution | manual | nothing writes `order_id` to the ledger, so every live fill must be hand-added to `known_own_order_ids` or the next cycle halts |

**N6 is the one that matters most.** With no exit path, a position opened on
Monday is held until someone intervenes. §4 of the specification promises five
exits and the live system implements none of them. Trading in this state would
have produced exactly the failure the pre-registration lists as serious — "no
position held past 15:50 ET" breached, not by variance but by absence.

The audit found this before the live run. That is the system working at the
level above the code.

Lower-severity findings — the spec omitting four sizing rejection rules (N15),
`evaluate_exit`'s docstring misstating its own check order (N10), the target
drifting with current SMA20 rather than entry-time (N11), a hard-coded 1.5 in
`run_cycle`'s stop display (N21), stale-bar-file globbing (N24), unread
duplicate config keys (N25) — are in the audit transcript and are being fixed
without separate ceremony.

## 3. Predictions that cannot be evaluated

`docs/PRE_REGISTRATION.md` promised seven outcomes measurable "from
`logs/decisions.jsonl` and the broker record." Three are not, as the engine
currently writes records:

| | Prediction | Evaluable | Why not |
|---|---|---|---|
| P1 | P&L in −0.6%…+0.1% | **yes** | final `total_asset` − 100,000 |
| P2 | Max drawdown < 0.6% | **no** | no equity is recorded on any cycle record; the broker exposes only a current snapshot |
| P3 | < 14 entries | yes | tagged buy fills |
| P4 | Win rate < 40% | yes | pair buy/sell fills |
| P5 | Zero limit breaches | yes | though clause 4 depends on exits nothing schedules (N6) |
| P6 | $0.99 buy / $1.00 sell | **no** | no fee field on orders, `account_order_fees` and `account_cash_logs` both dead; needs cash sampled around each fill |
| P7 | Median stop breach < 0.5 ATR | **no** | no exit record and no exit label, so a stop cannot be distinguished from a time exit that happened to be below the stop |

**I wrote seven predictions and asserted the ledger would support them without
checking that it would.** Three cannot be judged. A prediction that cannot be
evaluated is worse than no prediction: it looks like a commitment and settles
nothing.

Three record types fix all three, and none exists yet: a per-cycle
`account_snapshot` carrying equity, peak and drawdown; an `execute` record
carrying `order_id`, submitted quantity, fill and fee residual; and an `exit`
record carrying the rule that fired alongside the stop level and fill.

These go into the executor before any live trade. If they are not in place, P2,
P6 and P7 will be reported as **unmeasurable by our own instrumentation** — not
quietly dropped, and not retrofitted with a looser definition after the fact.

## 4. What the audit also confirmed

Not everything it checked was broken, and the confirmations matter as much as
the defects:

- The header hashes verify. `git show 5748462:docs/STRATEGY.md | shasum -a 256`
  returns `d2295d99…`; the config returns `c0ca0cf8…`; the commit timestamp is
  `2026-11-20T15:33:59Z`.
- **No strategy trade existed at that commit.** All seven orders in the account
  since January are accounted for: four `S00-PROBE-*`, one `S00-CANCEL-TEST`,
  one `S00-PROBE-002-FLATTEN`, and the two untagged ANT orders from the
  unidentified second writer. Six predate the commit; one follows it. None is a
  strategy trade.
- The gate's shrink-or-refuse invariant holds across the randomised sweep. The
  audit sharpened the claim: of 2,000 iterations, 1,910 reach the gate and 90
  raise in sizing first, so "tested across 2,000 randomised states" overstates
  by 90. Corrected wording: 1,910.
- C1's factual basis checks out — the notional cap binds on all five symbols,
  20/23/56/269/245 against risk-budget 138/108/411/2422/2136.
- The ledger API exposes append and verify only. Edit and delete are impossible
  through it, and tampering is detectable. The docstring's qualification about
  what the chain does *not* prove was found accurate.

## 5. The pattern worth naming

Three separate times now, a defect has taken the same shape: **a control that
is correct in isolation and starved by its caller.** The account guard compared
config against itself. The outlier filter read future bars. The kill switch
reads hardcoded zeros.

Each was found by something outside the component — a cross-implementation
comparison, an independent audit — and none by the component's own tests. Unit
tests that construct their inputs cannot detect a production path that
constructs them wrongly. That is a lesson about test design, not about these
three bugs, and it is the reason this audit was commissioned rather than
assumed unnecessary.
